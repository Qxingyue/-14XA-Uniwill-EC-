# FanCtl — 机械革命 无界14XA 风扇控制

Windows 平台的双风扇控制工具，直接操作同方（Uniwill）EC 的风扇寄存器：**主扇、副扇各自一条温度曲线**，可随时把控制权交还给 EC 原生策略。

图形界面用 Python + tkinter 写，命令行与 GUI 共用同一套核心库。

> 只在本机（MECHREVO 无界14XA / BIOS N.1.14MRO26）逐项实测验证过。其他机型请先只读测试，不要直接套用。

## 功能

| 功能 | 说明 |
| --- | --- |
| 四种运行模式 | 自动（交还 EC）/ 手动（维持固定占空比）/ 温度曲线 / 手动 + 副扇独立 |
| 双扇独立曲线 | 主扇一条、副扇一条，互不影响；也可以让副扇跟随主扇 |
| 快捷预设 | 静音 10%、安静 25%、日常 35%、均衡 50%、强冷 75%、全速 100% |
| 保护与临界 | 温度 ≥ 保护阈值强制全速；≥ 临界值立即交还 EC（默认 85℃ / 95℃） |
| 低温交还 | 曲线模式下 CPU < 45℃ 交还 EC，回升到 ≥ 48℃ 自动接管（仅曲线模式） |
| 两种控制后端 | 曲线表 + 锁存（默认，几乎零写入）/ 高频写占空比寄存器（25Hz） |
| 诊断日志 | 一键开启，JSONL 格式，变化驱动 + 10 秒心跳，异常自动加深 EC 快照 |
| 开机自启 | 注册计划任务（登录时启动，最高权限），可随时在「任务计划程序」删除 |
| 关窗即交还 | 关闭窗口 / 退出进程后 EC 在 6~8 秒内按自己的斜坡接管，不会把风扇卡在某个转速 |

## 运行前提

1. **Windows 10 / 11 x64**
2. **InpOutx64 端口驱动**（必需）

   程序通过设备 `\\.\inpoutx64` 向 EC 的 0x62/0x66 端口做读写事务，与厂商工具走的是同一条路径。这个驱动需要单独安装（Highresolution Enterprises 的 InpOut32/InpOutx64，免费），装好之后本程序**不需要管理员权限**即可运行。

   判断驱动是否就绪：设备管理器或驱动安装器里能看到 InpOutx64 已安装；否则程序启动会直接报「无法打开 inpoutx64 驱动」并给出错误码。

3. 用源码运行还需要 Python 3.9+（带 tkinter），以及 InpOutx64 对应位数的 Python（x64）。

## 使用

### 直接运行 EXE

到 [Releases](../../releases) 页面下载最新的 `FanCtl.exe`：单文件绿色版，双击即可运行，不需要装 Python，不写注册表、不装服务。

（可执行文件不进仓库：11 MB 的二进制会让每次发版都把仓库撑大一份，改走 Release 附件。）

### 从源码运行

```bat
pythonw FanCtl.pyw
```

### 命令行

核心库自带 CLI，适合脚本或排查：

```bat
python fanctl.py status                  :: 读一次状态
python fanctl.py watch                   :: 持续监视（只读）
python fanctl.py set 60                  :: 主扇 60%，副扇跟随
python fanctl.py set 40:80               :: 主 40% / 副 80%
python fanctl.py set 40:follow           :: 主 40%，副扇跟随
python fanctl.py curve 45:20,55:30,65:45,75:65,85:100
python fanctl.py curve 45:20,55:30,65:45 --curve2 45:25,60:40,70:60,85:100
python fanctl.py auto                    :: 交还 EC
python fanctl.py watch --backend duty    :: 切换控制后端
```

`set` / `curve` 会一直维持设定值，直到按 `Ctrl+C`；停止写入后 EC 会自己滑回去。

## 工作原理

### EC 事务必须串行

EC 的端口操作是一组三步非原子序列（写地址高字节 → 写地址低字节 → 读/写数据），中间被打断就会拿到别的寄存器的值。程序内部用一把类级可重入锁 `_port_lock` 把所有 EC 访问串起来，GUI 的采样线程和写入线程不会互相插队。

### 绝对写入，不做读-改-写

需要置位/清位时，一律按「已知基线值 | bit」和「已知基线值 & ~bit」直接写出，绝不先读回再改。读-改-写在多进程同时访问 EC 时会把别人的位一起改掉——本项目曾经因此把电源寄存器写坏，机器直接断电。

### 曲线表 + 锁存（默认后端）

EC 每 1~2 秒会用自己的策略覆写目标占空比寄存器，因此「写一次」是无效的。默认后端改为写入 EC 的自定义曲线表并置锁存位，让 EC 自己按我们给的表调：

- 表区每张 48 字节，实际只写**前 8 字节**（96 次写降到 16 次），避开容易被误伤的 `0x38` / `0x3A` 区；
- 取 8 字节中的最大值作为生效值，索引外补即可；
- 锁存位 `0x0727` bit6，隔离位 `0x07C5` bit7，退出时都清回 0。

`duty` 后端是旧行为：25Hz 持续写占空比寄存器，写入量大，只在需要精确跟随瞬时负载时用。

### 撕裂采样与自愈

第三方软件（厂商控制中心之类）也在访问 EC 时，极低概率会读到半新半旧的撕裂值，曾出现「温度 254℃」这类假数据。处理方式：

- 温度取多次采样的**众数**，超出 `0~120℃` 直接判废；
- 转速、占空比用指数平滑，> 60000 RPM 的读值直接丢弃；
- 每 5 秒巡检电源与静态寄存器，发现被写坏就恢复；表驱动模式每 10 秒对一次心跳，偏差超过 8 raw 才重锁，避免跟着争用一起狂写。

### 交还机制

以下情况都会主动交还给 EC 原生策略，并把锁存位、隔离位清回出厂值：

- 关闭窗口 / 进程退出；
- 温度 ≥ 临界阈值；
- 曲线模式下温度 < 45℃；
- 手动点「恢复到自动」。

交还后 EC 按自己的斜坡（约 3 raw/s）接管，完全可逆。

## 实测寄存器（本机）

| 用途 | 地址 | 说明 |
| --- | --- | --- |
| CPU 温度 | `0x043E` | 1 字节，℃ |
| GPU 温度 | `0x044F` | 本机无独显，恒为 0 |
| 主扇转速 | `0x0464/65` | 大端 16 位，RPM |
| 副扇转速 | `0x046C/6D` | 大端 16 位，RPM |
| 主扇占空比 | `0x1804` | 0~200 → 0~100% |
| 副扇占空比 | `0x1809` | 0~200 → 0~100% |
| 曲线表锁存 | `0x0727` | bit6 = 启用自定义曲线表，出厂 0x00 |
| 主副扇隔离 | `0x07C5` | bit7 = 输出隔离，出厂 0x00 |

`0x1800~0x1809` 是两条对称的 5 字节风扇记录，不是「寄存器 + 镜像」：

```
A: 上限 0x1801 = 0xC8   目标 0x1804  -> FAN1
B: 上限 0x1806 = 0xC8   目标 0x1809  -> FAN2
```

两路彼此独立，必须各自写，否则只控得住一把扇。

## 占空比下限

实测本机 3%~20% 全部稳定；**只有 0% 会让两把扇在 0~800 RPM 反复启停**。所以：

- 手动下限 `MANUAL_FLOOR_PERCENT = 5`；
- 「静音」预设给 10%（表后端下已接近 1745 RPM 的转速地板，比 20% 安静一档）。

## 诊断日志

GUI 底部勾选「诊断日志」后开始记录，文件落在程序同级的 `diag/` 目录：

- 格式 JSONL，每行一条，`kind` 分 `session` / `event` / `tick` / `alert`；
- 采样策略：温度、目标、占空比、转速、提示任一变化就记一条，平稳期每 10 秒补一条；
- 出现撕裂修复、电源守卫、端口争用、目标与实到长期不符时，自动附一份 EC 原始寄存器快照；
- 单文件超过 8MB 切新文件，目录最多保留 20 个；每条立即 flush（这台机器有过异常掉电，缓存日志会丢）。

默认关闭，不记录任何与风扇无关的内容。

## 已知限制

- 只在无界14XA / BIOS N.1.14MRO26 上验证。其他 Uniwill 机型寄存器地址和曲线表布局可能不同，直接套用可能无效甚至写坏配置——请先用 `status` / `watch` 只读确认。
- 主副扇给相同目标时（如 25% / 25%），本机观察到副扇会被 EC 判停转，转速掉到 0。需要副扇转就给它单独的值。
- EC 被第三方软件并发访问时，撕裂读无法从原理上根除（对方不配合加锁），只能靠众数滤波 + 周期性自愈兜底。
- `duty` 后端写入频率高，长时间运行会增加 EC 负担，日常用 `table`。
